# v0.2 verification and operational limits

## Reproducible release checks

```sh
bun install --frozen-lockfile
bun run check:lock
bun run lint
bun run typecheck
bun run test
bunx sproutboat check
bunx sproutboat build --standalone --target host
sh scripts/verify-binary.sh dist/risulta-sprout
```

CI and release workflows execute the same checks on native Linux x64 and
ARM64 runners. The release workflow checks static linking, both proxy modes,
checksums and the complete asset inventory before publishing. Use the
workflow logs for the exact artifact and commit, rather than treating a local
macOS build as a Linux result.

The binary verification script always uses disposable directories, generated
credentials and loopback ports. It runs from outside the checkout to prove
that assets are embedded. The recovery suite creates a snapshot, validates
its SQLite integrity, rejects a truncated copy, restores into a fresh directory,
starts a second instance of the same executable and checks accounts, site
permissions, analytics, annotations and public-sharing state. Scheduled
backups and rollups are exercised through the executable's maintenance child.

Installer fixtures cover fresh configuration, saved CLI forwarding, channels,
exact versions, checksums, paused writers, safety copies, failed readiness and
recovery state. These fixtures simulate systemd and downloads. In addition,
CI runs the real installer with systemd on disposable Ubuntu x64 and ARM64
runners: it installs the published v0.1.8 binary, creates traffic, upgrades
to the candidate executable through `risulta update`, checks a no-op update,
then restores the saved paired data and executable. Candidate download assets
and metadata are staged locally for this drill; actual HTTPS distribution is
checked by release publication. Caddy and other distributions are not covered. Perform a
fresh-install smoke check on a disposable Debian or Ubuntu server before
standardizing a new deployment environment. No destructive drills should run
against a production data directory.

## Safe restore checklist

1. Keep the previous data and executable together before updating.
2. Stop every Risulta writer before replacing the live database.
3. Validate the snapshot with `sqlite3 SNAPSHOT 'PRAGMA integrity_check;'`.
   The result must be `ok`. Do not use corrupt or incomplete files.
4. Restore the snapshot into a separate data directory first and run its
   matching executable on a loopback port. Verify login, site access and
   traffic before using it in production.
5. To restore production, preserve its database and WAL sidecars, copy the
   verified snapshot to `d1/DB.sqlite`, preserve ownership, then restart.
6. For a schema downgrade, restore the saved paired data, executable and
   configuration. Never run a schema-6 binary against a schema-7 database.

Restoring an earlier snapshot discards later traffic. Backups include private
account and session data. Store protected copies off the server.

## UI and feature limits

- Annotation dates are UTC dates, not exact timestamps. Today marks them at
  midnight. A website can have 500 notes, each at most 240 characters.
- Public widgets contain aggregates only, update every 60 seconds and use a
  30-second server snapshot cache. Existing embeds revoke on their next
  successful refresh. A permanently offline browser cannot receive revocation.
- Automatic themes honor explicit website preferences before OS preference.
- Geist is preloaded with optional font display. On a slow first navigation,
  readable fallback text remains until the next navigation, preventing a late
  font swap. A full cross-browser font timing matrix has not been measured.
- Funnels retain the documented 50,000-event cap. Raw events remain retained
  indefinitely. This release does not claim a general production capacity SLA.
- Production needs the standalone executable and SQLite data only. Bun,
  TypeScript and Python are development/verification tools, not server workers.
